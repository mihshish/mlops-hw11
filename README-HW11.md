**Стенд измерен в настоящем kind-кластере Kubernetes 1.34.0, все пять проверок прошли.** API использует CPU-имитатор; обучение и веса не нужны. ## Что подготовлено

Версия API выросла из HW8–10: FastAPI, тот же интерфейс StubBackend, фактическая идентичность загруженного артефакта, готовность после прогрева, проверка границ запроса. Дополнительно: вычислительный CPU-режим, очередь 2 running + 4 waiting, NDJSON с обязательным `done`, локальный LRU из четырёх префиксов, Prometheus Histogram, Grafana и rollout с drain. Всё явно отмечено `backend_mode=simulated`. Реальная модель и её веса не нужны.

В окружении хозяина прошли 7 локальных тестов и Helm lint. Отдельно выполнены настоящие Kubernetes-опыты:

- **A.** Преждевременная готовность: 20/61 запросов пришли в холодный Pod, после исправления — 0/61. Штатный выкат: 105 полных ответов, включая поток на 30 частей, без 5xx и обрывов. Неготовая B не получила трафик; после отката клиенты увидели A. Принудительная остановка оборвала поток по завершении 4 из 30 частей, восстановление записано отдельно.
- **B.** 12 прогонов по 120 с, 9600 попыток, четыре клиентских Pod с разными IP. При перекосе 80%: 563/2400 отказов с ClientIP и 2/2400 без него. Медиана p95 TTFC по трём таким повторам: 1,108 → 0,773 с.
- **C.** CPU HPA поднял число реплик до 3 и вернул к 2. Оба алерта прошли pending → firing → inactive. В отдельном нагруженном прогоне с ClientIP новая готовая реплика не получила ни одного запроса от четырёх уже привязанных клиентов.
- Четыре измеренных графика и 24 сверки счётчиков Prometheus с клиентскими запросами (24/24 совпали).

Файл лекции 11 отсутствовал: в отчёте указан первичный кейс Google Cloud / Vertex AI с оговоркой, что его принадлежность лекции не проверена.

Отдельно сохранён первый короткий провал до одной реплики при включении HPA через Helm и [проверка исправления](results/hpa-install-fix.json): повторное включение сохранило оба готовых Pod. Это контроль конфигурации, а не изменение данных старого опыта.

## Перед развёртыванием

1. Освободите **не менее 8 GiB** на диске Docker и временных файлов (рекомендуется 10 GiB). Не выполняйте `docker system prune`, WSL reset, factory reset или удаление чужих томов ради этой лабы. После освобождения места при необходимости штатно перезапустите Docker Desktop.
2. Нужны Docker Desktop с Linux containers, Git Bash с GNU Make, uv и Python 3.12, kind 0.30.0, Helm 3.19.0 и kubectl 1.34.x. Начальная версия Docker — 28.3.2; кластер — kindest/node:v1.34.0. Kubectl 1.32.2, поставленный Docker Desktop на этом ноутбуке, следует заменить отдельным 1.34.x для этих замеров. На этом ПК kind и Helm уже есть под `.runtime/bin`. Можно добавить туда `kubectl.exe` нужной версии либо установить его в PATH.
3. Проверяйте Docker CLI, а не наличие окна: `docker info`. **Обязательный настоящий кластер** не заменяется локальным uvicorn. Настройки kind лежат в `hw11/kind.yaml`: kube-proxy nftables, IPv4; для iptables-диагностики сохранены результаты отдельно от измерений. Образ API: примерно 51 МБ сохранённых слоёв, каталог containerd внутри kind измерен в 2,4 ГиБ; это не объём всей VHDX.
4. Все команды — из корня репозитория, Git Bash. Python-инструменты `hw11` по умолчанию обращаются только к `kind-mlops11`, namespace `hw11`.

```bash
make hw11-check       # локальные HTTP/учёт, 7 тестов, ~20 с
make hw11-up          # проверяет место до загрузок; собирает образ, ставит kind + Helm
make hw11-status      # Deployment / Pods / Services / EndpointSlice
make hw11-smoke       # один действительный поток к Service из клиентского Pod
```

Если после сбоя Docker не стартовал старый control-plane, но `docker info` работает, проверьте только этот кластер: `docker ps -a --filter name=mlops11-control-plane`, `kubectl --context kind-mlops11 get nodes`. Если этот стенд сломан и в нём нет нужных результатов, `make hw11-down` удаляет **только** кластер `mlops11`, затем `make hw11-up`. Сами результаты на диске хоста не затрагиваются.

Prometheus (5 с scrape, 6 ч / 96 MB TSDB, emptyDir максимум 192 MiB), Grafana (emptyDir 64 MiB), metrics-server v0.8.0. Для только локального self-signed kubelet включён `--kubelet-insecure-tls`; не переносить эту настройку в production. Для CPU/RAM Prometheus обращается к cAdvisor через Kubernetes API; RBAC узлов допустим только в выделенном учебном кластере. Grafana — анонимный Viewer на localhost при port-forward, не открывать наружу.

```bash
make hw11-grafana     # localhost, держать терминал открытым
# в браузере http://127.0.0.1:3000/d/hw11-observability
```

## Опыты и сдача

Запускать **последовательно**, по одной команде. B занимает около 27 минут с паузами, без обучения. A и C — дополнительно несколько минут каждый. Различают результаты каждого запроса, только окончание с NDJSON `done` — успех.

```bash
make hw11-a         # ранняя готовность → исправление → rollout → отказ B и откат → форсированный обрыв
make hw11-b         # 2 политики × 2 профиля × 3 повтора × 120 с, 9600 попыток
make hw11-c         # CPU HPA 2→3→2, привязка, два алерта
make hw11-verify    # 5 проверок, включая 3 живые Kubernetes
make hw11-collect   # сбор трасс, образов, PromQL и общего requests.jsonl
make hw11-report    # отчёт + до 4 графиков из реально существующих файлов
make hw11-audit     # быстрая сверка тестов и сохранённых данных — без повторной нагрузки
```

При несовпадении фактического результата с гипотезой сохраните сырые попытки, не подменяйте вывод. Если повторяете B после изменения кода, перенесите результаты предыдущей серии отдельно: скрипт переиспользует полные файлы по именам, чтобы возобновить *ту же* серию. Данными разных серий нельзя заполнять одну таблицу.

Скрипты используют отдельное соединение на запрос (`Connection: close`); четыре клиента — разные Pod/IP. IP, наблюдавшийся в API, фиксируется отдельно. Request ID, session ID и исходы есть в клиентской трассе и структурных логах сервера, не в labels. Для сравнения окон Prometheus не перезапускать до `hw11-collect`: emptyDir не переживает замену Pod мониторинга, а retention составляет 6 часов. Для уже опубликованной серии всё нужное собрано; не запускайте повторный collect по давним окнам.

После выгрузки данных: **`make hw11-down`** удаляет свой kind-кластер и его временную метрику. Медиа/образы других лаб не изменяются. Остаточные образы только своего стенда при необходимости просматривайте `docker image ls mlops11-api`. Журналы назначения и ожидаемые ограничения описаны в отчёте; точный размер стенда заполняется по `results/container-disk.json` после успешной установки.
